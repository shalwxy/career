## 파사드 단에서 검증한다 ✅ {#d-facade}
**2023 Q4 · 온체인 동기화.** 신규 코어 서비스 연동 시 잘못된 입력이 Saga 를 시작하면 보상 트랜잭션까지 번진다. 게임 서버가 호출하는 파사드에서 유효성 검사를 먼저 하고, 변환기는 단위 테스트와 함께, gRPC 서버는 코어 에러를 래핑한다. 이후 도메인별 유효성 검사기를 추가할 때의 기준점.

## [확인 대신 선점한다](#dg:saga) ✅ {#d-preempt}
**2024 Q1 · 캐릭터 민트 닉네임.** "존재하는지 확인한 뒤 생성" 은 확인과 생성 사이에 경합 창이 있다. 존재 확인을 제거하고 Redis 분산 락으로 선점, 선점은 Saga 메시지 처리 시점에, 해제는 성공 시에만. 처음엔 "실패 시 해제" 로 짰다가 정정했다. 캐릭터 생성에도 같은 락 적용. 이 원칙이 이후 Redis NX dedup, Lua 원자 카운트의 원형. 현재 해당 조직은 같은 원칙을 Event Sourcing 기반으로 재구현했다.

## 검증은 단건 반복이 아니라 목록 조회로 ✅ {#d-validator}
**2024 Q1.** NFT 아이템 등록/해제 검증이 건마다 상태 서비스를 호출하던 것을 목록 조회 1회로. 검증기 에러 타입을 통일해 호출자가 분기하기 쉽게.

## test/qa 승격 전 dev 선행 배포 ✅ {#d-devfirst}
**2024 Q1 · Helm 운영.** DE 서비스 배포 시 test/qa 승격 전에 dev 에 먼저 올려 검증하고, 장애 재현용 임시 배포/롤백은 커밋으로 남겨 "언제 무엇을 올렸다 내렸는지" 가 이력에 남게.

## 레이어를 나누고 컨슈머를 일반화한다 ✅ {#d-split}
**2024 Q2 · 트랜잭션 이력.** 거래 결과 전용이던 컨슈머를 범용 이벤트 컨슈머로 일반화하고, 레이어 재정비, 쓰지 않는 기능 제거, 메시지 포맷 v2. 이후 내가 만든 서비스의 기본 구조.

## 북마크는 멱등이 기본 ✅ {#d-idempotent}
**2024 Q3.** 더블클릭·재시도가 흔하다. 중복 요청은 성공 반환, 해제는 미존재 시 실패로 명확히, 카운트는 DB 저장 성공 시에만 증가. 카운트 캐시는 0 이하면 키를 제거해 "틀리면 재계산" 이 가능한 쪽으로.

## proto 저장소는 도메인별 모듈로 ✅ {#d-proto}
**2024 Q3.** 단일 proto 패키지에서 한 도메인 변경이 전 서비스 리빌드를 유발했다. 도메인별 독립 모듈·태그로 재구성, 생성은 1회, 게이트웨이 descriptor 는 CI 가 push. 폴더 구조 변경은 소비 서비스 전부를 깨뜨리므로 **한 번에** 해야 한다는 걸 revert 반복으로 배움. 같은 이유로 공통 라이브러리에서 proto 의존을 떼는 마이그레이션을 플랫폼·거래소 서비스 6곳에 2주 안에 연속 적용.

## 트랜잭션 해시를 유니크 키로 ✅ {#d-unique}
**2024 Q4.** 기존 복합 키로는 같은 트랜잭션을 구분할 수 없어 중복 저장이 발생. 트랜잭션 해시 컬럼을 추가해 유니크 승격. 소모성 아이템은 판매자 주문 해시가 충돌해 구매자 주문 해시를 저장. 이후 크로스체인 도메인에서는 이 키가 "계속 바뀌는 값" 이라 안정 키가 아니라는 게 드러나 상관관계 키를 따로 둠.

## 비정상 이벤트는 DB 가 아니라 DLQ ✅ {#d-dlq}
**2024 Q4.** "저장하되 조회에서 제외" → 3주 뒤 "DLQ 로 보내고 DB 에 쓰지 않음" 으로 변경. 비정상 row 가 DB 에 남으면 조회 필터와 정합성 집계가 흐려진다. DLQ 재처리 쪽이 운영 추적이 쉽다.

## 카운트는 요청 경로가 아니라 이벤트로 ✅ {#d-count}
**2024 Q4 ~ 2025 Q1.** Redis 캐시 → Kafka 이벤트 발행 → 이벤트 수신 기반 집계 → 전용 컨슈머 분리. 요청 경로에서 동기 갱신하면 레이턴시·정합성이 함께 나빠진다. 정합성 복구용 리셋 RPC 를 두어 "틀어지면 코드보다 리셋 먼저".

## 페이지네이션은 커서로 🔁 {#d-cursor}
**2024 Q2 → 2025 Q1.** 공통 파라미터와 전체 건수 를 먼저 노출했다가, 테이블이 커지며 count 비용이 문제가 되어 커서(커서 키) 기반 무한 스크롤로 전환. 첫 페이지만 캐시. **교훈**: 전체 건수 를 한 번 노출하면 프론트가 의존해 빼기 어렵다 — 처음부터 커서였어야.

## [동시 적재 정합성 — NX + advisory lock](#dg:activity-lock) ✅ {#d-lock}
**2025 Q2~Q3 · 크로스체인 전송.** 메시지 순서 비보장 + 재시도로 요청/결과 동시 적재·중복 발생. 이벤트 종류별로 방어를 달리했다 — 거래·자산·Swap 은 Redis SET NX(TTL, 처리 후 해제)로 동시 중복 처리만 막고, 순서가 뒤집히는 Warp 요청/결과는 nullable 스키마 + 트랜잭션 범위 advisory lock(네임스페이스 키 + 해시 버킷 키, 버킷 상한 설정) 아래에서 선조회 후 생성/수정(먼저 온 쪽을 PENDING·NO_CONTENT 상태로 선행 적재). 락의 의도는 "요청↔결과 동시 적재 방지" 이지 "결과 자기 중복 방지" 가 아님을 나중에 명문화.

## [서비스는 데이터 파이프라인에 직접 쓰지 않는다](#dg:cdc) ✅ {#d-cdc}
**2025 Q2 → 2026 Q1.** 요청 경로에서 데이터 레이크에 직접 적재하던 실험을 취소하고 배치로 분리(2025 Q2) → Kafka publish 로 적재(2025 Q3) → 커밋 후 publish 실패 유실 때문에 **CDC** 로 전환(2026 Q1). CDC 는 DB 커밋이 곧 발행. 상태성/이력성 테이블 구분, slot keepalive, 조건부 task 까지 세트로.

## [벤더 응답은 200+outcome 과 에러로 분기](#dg:creditcard) ✅ {#d-worldpay}
**2025 Q3 · 신용카드 인증.** 벤더가 400대/500대에 실패를 섞어 반환. 400대 대부분은 사용자가 고칠 수 있는 실패라 200 + outcome 코드로 프론트가 안내를 분기하게, 500대는 벤더 장애라 에러로 재시도 유도. 같은 결제수단 조합으로 짧은 시간에 시도가 몰리면 일정 시간 차단하는 장치도 추가(2025 Q4, 이후 정책 서비스로 이관·고도화). 400/500 분기는 리뷰를 거쳐 정한 것.

## 일일 횟수 카운터는 Lua 로 🔁 {#d-lua}
**2025 Q3.** "증가 + 첫 증가 시 만료 설정" 을 Lua 한 번에 — 키 생성과 TTL 설정 사이의 틈 제거. 날짜는 키가 아니라 만료 시각(UTC 자정)에. 한도 **확인은 아직 Lua 밖** 이라 동시 요청 시 초과 여지가 남아 있다 — 확인까지 Lua 에 넣어야 완전한 원자성이라는 것이 회고. 대역별로 횟수를 다르게 두는 설정은 곧 **revert** — 2026 Q4 에 시간 정책만 설정으로 외부화.

## 통합 알림 — 3가지 결정 ✅ {#d-notify}
**2025 Q3~Q4.** (1) "모든 사용자에게 알림" 기능 제거 — 대량 fan-out 은 알림 서비스가 지지 않는다. (2) URL·타이틀·본문을 백엔드에서 생성 — payload 인터페이스 확장과 URL 생성을 맡아 프론트별 조립 중복 제거. (3) JWT 검증을 자체 흡수 — SSE 연결마다 계정 서비스를 호출하던 비용 제거. 

## 캐시 무효화 대신 짧은 TTL ✅ {#d-ttl}
**2025 Q3 · 거래소 BFF.** 북마크 변경 시 캐시 무효화 → 비동기 무효화 → context 취소로 실패 → timeout 10s/30s/1m 으로 늘리다가 **3초 TTL, 무효화 없음** 으로 수렴. 무효화 경로가 요청 context 에 묶이면 실패 모드가 늘어난다. 3초 stale 은 UX 상 허용 가능.

## 컬럼 이름에 용도를 넣지 않는다 🔁 {#d-naming}
**2025 Q4 ~ 2026 Q2.** 해시 컬럼 이름을 기획 변경에 맞춰 세 번 바꿨고(검사 자체가 제거되기도), 정책 테이블·필드 이름도 여러 번. 이름이 바뀔 때마다 DBA 검토·마이그레이션·리뷰가 따라붙는다. 중립적 이름을 처음부터.

## [롤백 토픽 대신 결과 토픽](#dg:usdt) ✅ {#d-settle}
**2025 Q4 · 스테이블 코인 선차감.** 선차감 후 별도 롤백 토픽을 두면 순서·중복 처리가 두 배. 트랜잭션 결과 토픽에서 성공/실패/드랍을 받아 실패일 때만 선차감을 되돌림(선차감이 곧 확정). 토큰 종류는 enum 으로 받아 추가 시 테이블 변경이 없게.

## [정책 전용 서비스로 분리](#dg:sentinel) ✅ {#d-sentinel}
**2026 Q1.** 제어 로직이 공통 라이브러리·계정·블록체인 서비스에 흩어져 있었다. 1단계로 계정 서비스·공통 라이브러리의 제어 로직을 포털 서비스로 모았으나 콘텐츠 도메인과 섞여 **정책 전용 서비스**를 신설. refresh 를 각 서비스가 전체 정책을 메모리에 올리던 방식에서 정책 서비스가 단일 소유자가 되는 구조로(메모리 이슈). 이후 블록체인 서비스의 화이트리스트까지 이전해 통합 완료.

## [서비스 신설은 배포 세트까지](#dg:cicd) ✅ {#d-deployset}
**2026 Q1 · api-sentinel.** 코드만 넘기고 배포 설정을 뒤로 미루면 dev 에서만 도는 서비스가 된다. Helm 템플릿 · 4개 환경 매니페스트 · Envoy route · CI 배포 job 을 복제해 코드와 같은 주에 한 세트로 넣었다. 새로 설계한 것은 없고, 있는 패턴을 빠짐없이 따라간 것. [dev 선행 배포](#d-devfirst) 원칙과 짝.

## jitter 와 cadence — timer 를 택한 이유 ✅ {#d-jitter}
**2026 Q1.** 정책 refresh 가 같은 경계에 몰려 스파이크. ticker 로 고정 주기를 잡아봤지만 인스턴스 간 위상이 같아 분산이 안 됨 → 매 회차 `refreshTTL ± 5s` 랜덤 **timer** 로 확정. fixed window 는 한 번 제거했다가 다시 둘 다 지원.

## 정책은 코드 분기가 아니라 enum/설정으로 ✅ {#d-enum}
**2026 Q2~Q3.** 출금 가드가 "OTP 냐 잠금이냐" 를 몇 번 왕복했다. 정책은 바뀐다 — API 가 어떤 검사를 할지 **enum 으로 받게** 해 왕복이 코드 변경으로 번지지 않게. 같은 이유로 토큰 종류·시간 정책도 설정/enum 으로.

## 롤백에서 배운 것 ↩️ {#d-rollback}
**2026 Q3 · 출금 지연 피처.** 7개 서비스에 걸친 피처가 기획 변경으로 전체 롤백. 그 과정에서 찾은 기존 결함 — DB 에러를 삼켜 "commit unexpectedly resulted in rollback" 을 내던 경로, 알림 발행이 커밋 전에 일어나는 경로, 갱신 조건이 식별자가 아닌 문제 — 을 수정했지만 피처와 한 커밋 흐름에 섞여 있어 **롤백에 함께 되돌아갔다**. 결함 수정은 피처 브랜치와 분리해 먼저 머지해야 롤백에서 살아남는다는 것, 큰 피처는 **브랜치 + 메모** 를 남겨야 재개 비용이 준다는 것을 배웠다. 되돌아간 수정은 재적용 과제로 인수인계에 기록.

## 잠금은 Redis 가 아니라 컬럼으로 ✅ {#d-lock-email}
**2026 Q3 · 이메일 변경 후 보안 설정 잠금.** Redis TTL 이면 기간 변경이 기존 키에 반영되지 않고 영속성도 없다. 변경 시각 컬럼으로 전환. 선검사 API 를 따로 두면 프론트 호출이 하나 늘어 응답 필드 하나로 통합. Primary 조회로 복제 지연 창 제거, 설정이 0 이면 조회 생략.

## 외부 side effect 는 Outbox 로 🔄 리뷰 중 {#d-outbox}
**2026 Q4 · 디스코드 역할 동기화 (미머지 브랜치).** 팀의 트랜잭션 이벤트(Outbox) 모듈을 활용. 상태 변경 뒤 외부 API 호출(디스코드 역할 부여 등)을 inline + 로그로 끝내지 않는다. 트랜잭션 Outbox 에 이벤트를 쓰고 워처가 백오프 재시도, 부분 실패도 에러로 승격해 재시도가 걸리게. "배치가 나중에 주워 담는다" 는 복구 설계가 아니다 — 리뷰 지적에서 원칙으로.

## [대량 수신자는 streaming RPC 로](#dg:notification) ✅ {#d-stream}
**2026 Q4 · 백오피스 알림.** 수만 건 수신자가 상세 조회 응답에 통째로 실렸다. 상세에서 제거하고 500건 청크 스트리밍 RPC 로 분리, 상한 명시. 수신 규약(대상은 chunk 프레임으로만, 섞여 와도 무시)을 수신측 코드에 명시. 갱신 시 빈 목록이 오면 덮어쓰지 않아 실수로 대상 전체가 날아가는 사고 방지.

## [LLM 호출 내성](#dg:errorbot) ✅ {#d-llm}
**2026 Q4.** 벤더가 모델을 폐기해 404. 모델 교체 + 429/5xx 재시도(Retry-After 우선, 지수 백오프 + 지터, 4xx 영구 실패는 제외) + 동시 실행 세마포어 + 에러를 문자열 매칭이 아닌 타입으로 분기 + 테이블 테스트. 나흘 뒤 교체한 모델마저 폐기돼 재교체 — **교체 전에 벤더 카탈로그에서 가용 모델을 확인하고 닫을 것**.

## 배치는 continue-and-count 🔄 리뷰 중 {#d-batch}
**2026 Q4 · 디스코드 역할 동기화 배치 (미머지 브랜치).** 항목 실패는 failed 로 집계하고 계속 진행, 종료 시 성공/스킵/실패 요약. 목록 조회 실패만 중단. 리뷰 지적에서 원칙으로.

## 반복된 패턴

1. **기획 변경 롤백이 잦다** — 큰 피처는 브랜치 유지 + 메모.
2. **네이밍이 거듭 바뀐다** — 이름에 용도·토큰명을 넣지 말 것.
3. **서비스가 직접 외부에 쓰지 않는다** — 배치 → publish 제거 → CDC, 그리고 Outbox.
4. **정책은 enum/설정으로** — 코드 분기로 박으면 왕복이 커밋으로 번진다.
5. **리뷰 2회차가 기본** — 결제·보안은 1회차로 끝내지 않는다.
