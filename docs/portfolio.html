작업 철학은 네 가지입니다. 실패 경로부터 설계한다(롤백·재시도·멱등이 본체), 확인 대신 선점한다(존재 확인 후 생성은 경합 창이 있다), 서비스는 데이터 파이프라인에 직접 쓰지 않는다(Outbox 또는 CDC), 정책은 코드 분기가 아니라 설정/enum 으로 받는다.

1. 온체인-오프체인 동기화 — 유효성 검사와 닉네임 선점

2023-11 ~ 2024-04 Go · gRPC · Redis · Saga

맥락. 게임 자산(아이템·캐릭터·재화·닉네임)의 오프체인 상태와 온체인 트랜잭션을 Saga 로 동기화하는 조직에서 첫 업무를 시작했습니다. 게임 서버가 호출하는 gRPC 파사드(business-provider)와 Saga 실행기(saga-provider), 이벤트 저장소(event-service)를 다뤘습니다. 입사 첫 5개월의 작업이라 규모는 작지만, 이후 작업 방식의 출발점이 된 것들입니다.

유효성 검사 추가·보완. 신규 코어 서비스 연동 코드를 BP(파사드)에 만들면서 입력 유효성 검사, proto ↔ 도메인 변환기(단위 테스트 포함), gRPC 에러 래핑을 추가했습니다. 이어 Saga v2 전환 브랜치에서 재화(neso/currency)·캐릭터 유효성 검사기를 추가하고, nft_item 검사가 건마다 상태 서비스를 호출하던 것을 목록 조회 1회로 바꿨습니다.

닉네임 중복 생성 수정. 캐릭터 민트 시 “닉네임이 존재하는지 확인한 뒤 생성”하던 방식은 확인과 생성 사이에 틈이 있어 같은 닉네임이 두 번 만들어졌습니다. 존재 확인을 없애고 Redis 락으로 닉네임을 먼저 선점, 해제는 민트 성공 시에만 하도록 고쳤고 캐릭터 생성에도 같은 방식을 적용했습니다. 작은 수정이지만 “확인 대신 선점” 은 이후 작업에서 계속 쓴 방식입니다.

운영. Helm 으로 신규 서비스를 롤아웃하면서, 장애 재현을 위한 임시 배포/롤백을 커밋으로 남기고 test/qa 승격 전 dev 선행 배포를 관행으로 정립했습니다.

관련 설계 결정: 확인 대신 선점 · 검증은 목록 조회로

2. 트랜잭션 이력 플랫폼 — 구조 개선부터 CDC 전환까지

2024-06 ~ 2026-11 Go · Kafka · PostgreSQL · Redis · Snowflake

맥락. 플랫폼의 블록체인 트랜잭션(거래·민팅·전송·크로스체인 전송·스테이블 코인)을 수집·조회·알림 발행하는 서비스. 초기 코드를 넘겨받은 2024년 6월부터 2년 반, 가장 오래 담당했습니다.

Deep dive — Kafka 순서 비보장과 동시 적재. 크로스체인 전송은 “요청 정보”와 “결과” 메시지가 역순으로 올 수 있고 재시도도 발생합니다. 단순 “exists → insert” 로는 중복이 생겼습니다. → 스키마는 순서 비보장을 전제로 nullable 설계, 애플리케이션은 Redis NX 로 “먼저 잡은 요청만 처리”, DB 는 트랜잭션 범위 advisory lock(키 2개, 상한 설정)으로 요청/결과 동시 적재를 막았습니다. 2026년 워프 지연 작업 때 락 시드와 조회 키를 다시 맞추는 보완이 한 번 더 있었습니다.

Deep dive — 롤백된 피처에서 남긴 것. 2026 Q3 에 보안 요건으로 “출금 지연” 피처를 7개 저장소(서비스 4 · proto · DDL · 게이트웨이)에 걸쳐 구현했으나 기획 변경으로 전체 롤백됐습니다. 롤백을 조율하면서, 그 과정에서 발견한 결함 수정 — DB 에러를 삼켜 “commit unexpectedly resulted in rollback” 을 내던 경로의 통일, 알림 발행 타이밍 수정, 갱신 조건을 식별자 기준으로 고정 — 은 되돌리지 않고 남겼습니다. 큰 피처가 사라져도 숨은 결함을 고친 가치는 보존된다는 걸 배웠습니다.

관련 설계 결정: 유니크 키 승격 · 동시 적재 정합성 · publish 대신 CDC · 롤백에서 남긴 것

3. 북마크 · 조회수 서비스 신설과 거래소 BFF

2024-06 ~ 2025-09 Go · gRPC · Kafka · Redis

북마크 서비스(서버). 초기 뼈대 직후 합류해 proto 설계부터 라이브까지 메인 담당(리포 커밋 과반). 북마크는 더블클릭·재시도가 흔해 멱등이 기본이어야 했습니다 — 중복 요청은 성공 반환, 카운트는 DB 저장 성공 시에만 증가, 0 이하면 캐시 키 제거. 카운트 갱신은 요청 경로의 동기 처리에서 Kafka 이벤트 기반으로 옮겨 레이턴시와 정합성을 함께 잡았고, 하루/총량 제한과 회원 탈퇴 연동을 더했습니다.

거래소 BFF(소비자). 같은 서비스를 소비하는 거래소 웹 BFF 도 직접 마이그레이션해, 서버 proto 변경이 BFF 에 어떻게 닿는지 양쪽에서 확인했습니다. 인벤토리 서비스 신설, 조회수 증가 비동기화, 캐릭터 이미지 렌더 병렬화·bulk 호출, 외부 조회 chunk 분할.

장애 — 간헐적 pod 재시작. 원인 불명으로 BFF pod 가 재시작되던 문제를 로그 추적으로 비동기 반복문 안의 gRPC 호출이 자원을 점유하는 것으로 좁히고, timeout 과 chunk 호출로 해결했습니다.

캐시의 교훈. BFF 북마크 캐시를 “변경 시 무효화” 로 설계했다가 비동기 무효화 실패·context 취소 문제로 timeout 을 늘려가던 끝에 3초 TTL, 무효화 없음 으로 단순화했습니다. 무효화보다 짧은 TTL 이 낫다는 걸 체감한 사례입니다.

같은 시기. 전사 proto 저장소를 도메인별 모듈로 재구성하고, 공통 라이브러리 마이그레이션을 플랫폼·거래소 서비스에 같은 주에 적용했습니다. Java/Spring Kafka 컨슈머에 북마크 이벤트 적재를 추가했고(이후 요구 변경으로 제거), 확률 고지 서비스의 요구사항 분석·버저닝·데이터 적재, 백오피스 제재 기능(단건·일괄·대량)과 제재 이력 화면을 공동 구축했습니다.

관련 설계 결정: 북마크 멱등성 · 무효화 대신 TTL · proto 모듈화

4. 신용카드 인증 · 재인증 — Worldpay 3DS

2025-08 ~ 2026-07 Go · Redis Lua · 결제 보안

맥락. 사용자가 등록한 신용카드를 0원 결제(3DS)로 검증하고 토큰화해, 이후 OTP 리셋·보안 설정 변경의 재인증 수단으로 쓰는 기능. 결제 보안의 가장 민감한 영역이라 리뷰를 2회차까지 돌리며 완성했습니다.

설계가 복잡했던 지점. - 벤더 응답 분기 — 벤더는 실패를 400대와 500대에 섞어 반환합니다. 400대 대부분은 사용자가 고칠 수 있는 실패, 500대는 벤더 장애. 400대는 200 + outcome 코드로 바꿔 프론트가 안내를 분기하게 하고, 500대만 에러로 올려 재시도를 유도했습니다. - 일일 3회 제한의 원자성 — incr 후 조건 분기로는 동시 요청에서 한도를 넘길 수 있습니다. Redis Lua 스크립트로 “확인 + 증가 + TTL” 을 원자 처리하고, 키에 날짜를 넣지 않고 TTL 로만 관리해 자정 reset 의 애매함을 없앴습니다. - 암호화와 서킷 브레이커 — 결제수단·발급사 정보를 암호화하고 카드 소유자 정보 비교를 해시 기반으로 전환했으며, 벤더 호출에 fail-fast 서킷 브레이커를 도입했습니다. - OTP 리셋용 재인증 — “새 카드 인증 / 기존 카드 재사용” 두 타입을 설계하고 일일 한도를 합산 적용, 벤더 오류는 횟수에서 차감하지 않았습니다.

결과. 2025 Q4 라이브 승격 후 재인증·OTP 리셋 재인증으로 확장되며 운영 중. 기획 변경(소유자명 검사 제거 등)에 따라 네이밍과 정책을 세 차례 조정하며 “컬럼 이름에 용도를 넣지 말 것” 이라는 교훈을 얻었습니다.

관련 설계 결정: 벤더 응답 분기 · Lua 원자 처리 · 네이밍 교훈

5. 스테이블 코인 도입과 선차감·롤백

2025-10 ~ 2025-12 Go · Kafka · 블록체인

온체인에 기록되기 전 발생할 수 있는 리스크(한도 초과, 중복 출금)를 막기 위해 오프체인에서 먼저 차감하고 결과에 따라 롤백하는 서비스를 스테이블 코인(USDT) 도입에 맞춰 재설계했습니다. 별도 롤백 토픽을 두는 대신 결과 확정 토픽 하나에서 성공/실패를 받아 롤백 여부를 결정해 순서·중복 처리를 단순화했고, 같은 nonce 로 여러 트랜잭션이 들어오는 케이스의 보정을 넣었습니다. 토큰 추가 시 enum 만 늘리면 되도록 테이블을 재설계했습니다.

관련 설계 결정: 롤백 토픽 → 결과 확정 토픽

6. 통합 알림 서비스 — SSE 와 streaming RPC

2025-07 ~ 2026-11 Go · SSE · gRPC streaming · MongoDB

  • 계정 서비스를 호출해 하던 JWT 검증을 알림 서비스가 자체 흡수해, SSE 연결마다 계정 서비스를 때리던 비용과 의존을 제거했습니다.
  • “모든 사용자에게 통합 알림” 기능은 기획과 합의해 제거 — 대량 fan-out 은 알림 서비스가 지지 않습니다.
  • 알림 URL·타이틀·본문을 백엔드에서 생성해 프론트별 조립 중복을 없앴고, 동시 구독 커넥션 상한과 메트릭을 두었습니다.
  • 백오피스 알림의 수신자 목록(수만 건)이 상세 조회 응답에 통째로 실리던 것을 gRPC streaming RPC(500건 청크, 상한 명시)로 분리하고, 수신 규약(“대상은 chunk 프레임으로만”)을 수신 측 코드에 명시했습니다. 큰 응답을 쪼개는 것보다 수신측이 어떻게 조립하는지를 정하는 게 설계의 핵심이었습니다.
  • 게이트웨이의 gRPC 의존을 HTTP 로 전환해 서비스 간 결합도를 낮췄습니다.

관련 설계 결정: 통합 알림 3가지 결정 · recipients 스트리밍

7. 정책 서비스 신설 — rate limit · ACL · feature flag · lockout

2026-01 ~ 2026-11 Go · Redis · PostgreSQL

문제. 서킷 브레이커는 공통 라이브러리에, rate limit 은 계정 서비스에, 화이트리스트는 블록체인 서비스에 — 제어 로직이 흩어져 중복과 운영 혼란의 원인이었습니다.

접근. 1단계로 기존 서비스가 흡수한 뒤, 콘텐츠 도메인과 섞이지 않도록 정책 전용 서비스를 신설했습니다. rate limit 정책 refresh 를 각 서비스가 전체 정책을 메모리에 올리던 방식에서 정책 서비스가 단일 소유자가 되는 구조로 옮겨 메모리 이슈를 해결했고, sliding/fixed window 를 모두 지원하되 refresh 스파이크를 jitter 로 완화했습니다(ticker → timer → ticker 로 돌아온 이유: cadence 안정성). 이어 OTP 반복 실패 잠금(lockout) 을 실패 횟수 보존/초기화 정책을 유연하게 설계해 추가하고, 블록체인 서비스의 화이트리스트까지 이전해 통합을 완료했습니다.

결과. 로그인 rate limit, 출금 화이트리스트, 백오피스 lockout 의 단일 진입점.

관련 설계 결정: 정책 전용 서비스 분리 · jitter 와 cadence · 정책은 enum 으로

8. PostgreSQL CDC → Snowflake 파이프라인

2026-06 ~ 2026-11 Debezium · Kafka Connect · Snowflake

데이터 팀이 운영 DB 변경을 더 빠르게 조회하길 원했고, 기존 배치 동기화 잡은 지연과 잡별 코드 유지 비용이 있었습니다. Debezium 으로 변경 이벤트를 Kafka 로 흘리고 Snowflake Stream/Task 로 적재하는 파이프라인을 구축했습니다.

  • replication slot keepalive 배치 — 변경이 뜸한 테이블의 slot 이 밀려 WAL 디스크가 차는 것을 방지.

9. LLM 에러 분석 봇과 모델 폐기 장애 대응

2026-07 ~ 2026-11 Go · Vertex AI · Slack API · OpenSearch · GitLab API

문제. 운영 에러가 Slack 에 들어오면 담당자가 매번 “어느 코드인지”, “전에도 봤는지”를 수동 검색. 밤·주말 대응이 느렸습니다.

솔루션. 스택트레이스에서 파일을 추출해 각 파일의 최근 커밋을 GitLab API 로 조회해 회귀 후보를 프롬프트에 주입하고, 과거 분석을 OpenSearch 에 signature 키로 저장해 재사용·dedupe·escalation. 최초 감지 시각과 스레드 영구 링크를 함께 응답합니다. Slack 긴 메시지의 preview 잘림을 감지해 원문을 재조회하는 방어, 에러 폭주 시 LLM 동시 실행을 세마포어로 제한하는 보호를 넣었습니다.

장애. LLM 벤더가 사용 중 모델을 폐기(404)해 봇 전체가 멈췄습니다. 모델 교체에 그치지 않고 429/5xx 재시도(Retry-After 우선, 지수 백오프 + 지터), 에러 메시지 타입 분기, 테이블 테스트까지 3일 내 랜드했습니다. 일주일 뒤 같은 알림이 재발해 “교체 전에 벤더 카탈로그에서 가용 모델을 확인했어야” 한다는 교훈을 남겼습니다.

관련 설계 결정: LLM 호출 내성

10. 그 외

  • KYC 벤더 마이그레이션 — 글로벌 규제 대응으로 전 사용자 KYC 데이터를 신규 벤더로 이관. 벤더 호출 한도 상향, 재진입 가능한 커서, 병렬 실행, rate.Limiter 로 안정화. 항목 실패는 집계 후 계속 진행하고 종료 시 요약하는 continue-and-count 를 배치 원칙으로.
  • 디스코드 자동 뱃지 — 게임 내 달성도에 따라 역할을 자동 부여. 비동기 → 동기 전환으로 누락 방지, 연결 해제 시 식별 정보는 보존, 외부 side effect 는 Outbox 재시도로.
  • 이메일 변경 후 보안 설정 잠금 — Redis TTL 에서 DB 컬럼 영속화로 전환, 선검사 API 대신 응답 필드 하나로 UX 통합, Primary 조회로 복제 지연 창 제거.
  • 운영 콘솔 — 디스코드 메시지 재전송(rate limit·변경 감지), 권한 도메인 분리, 지갑↔SNS 조회.
  • 그 밖의 운영 기여 — 담당 서비스 전부의 DB DDL·CDC·Kafka Connect SQL 을 DBA 검토를 거쳐 관리(103 커밋), Envoy 게이트웨이 route·transcoder 설정(82 커밋), 커뮤니티 공지 → 디스코드 크롤러와 역할 동기화 배치, 거래소 런칭 전 네비게이터·게임데이터 버그 픽스, 트레이싱을 Datadog 에서 Jaeger 로 전환.
